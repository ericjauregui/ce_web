# Order email presentation

The customer receipt is rendered by `templates/emails/order_receipt.html`, with matching copy in `order_receipt.txt`. `domains/emailing.py` supplies the existing normalized order snapshot, the sender inbox for contact links, the existing inline logo CID, and the saved submission timestamp (displayed in America/Los_Angeles time as PST or PDT when available). Customer names are not split for personalization. SKU codes identify unique items; every submitted line and its notes remain visible. Quantities have no inferred unit or monetary values. A 56px Photo column embeds the original local product photos as CID images, once per distinct filename. Missing images are omitted; the entire column is omitted when no photos are available. Product text stays visible independently. Only files inside static/product_images with supported image extensions can be embedded. The PDF still receives the existing product images.

This change preserves the current Graph transport, subject, From, customer To/staff BCC routing, fallback/retries, order persistence, CSV generation, and PDF attachment. There is no explicit Reply-To header today, so replies continue to use From; the contact CTA uses that same configured sender. No separate staff send was introduced because this task is limited to presentation. Staff receive the same customer-safe receipt by BCC. Thumbnail MIME parts are added for the new photo column; the existing signature inline attachment is preserved but no longer referenced in the HTML. There are no changes to checkout or site styling.

Local validation on 2026-09-20: 16 email unit tests passed with mocked Graph delivery, covering routing/MIME, PDF presence, existing retries, escaping, optional data, repeated SKU notes, unique counts, and preservation of 100 order lines. The PostgreSQL checkout integration test was skipped because no dedicated TEST_DATABASE_URL was configured. A synthetic three-line receipt measured 10,415 HTML UTF-8 bytes before provider processing (not counting its MIME images/PDF).

Codex in-app browser layout checks passed at 320, 375, 390, 430, and 900 CSS pixels; the content width caps at 600px. Long SKU/email fixtures passed at all four mobile widths. These are browser checks, not email-client certification. Real delivery, reply behavior, provider processing, image blocking, and Apple Mail/Gmail/Outlook light/dark-mode behavior remain untested. Very large receipts retain every line and can exceed the typical-order byte target; no truncation or overflow workflow was added.

The receipt displays codes without product names (including image alternatives), with clickable Google Maps shipping/business addresses and a Cell contact above Office. The plain-text alternative also uses codes and includes the Cell number.

The Photo heading is visually empty (accessible label retained), and line notes have their own wrapping Notes column between Item and Qty. Mobile layout was checked with multiline and long unbroken notes at 320/375/390/430px. On this follow-up, 14 email tests passed and two existing signature attachment tests failed because static/assets/ce_email_signature.png was deleted separately in the working tree.

A compact black/gold Follow us card appears directly after Your order notes and before Questions or changes (also when order notes are absent). Its labeled pill buttons use embedded PNG exports based on the site outline icons, with ordinary HTTPS social profile links and live text labels. The 320px browser preview fits without overflow. The 14 tests unrelated to the missing signature asset pass; the two known signature-dependent tests were excluded from this focused run.
